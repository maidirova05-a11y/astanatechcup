# Backend standard

Short reference for how server code is organised here. Follow it when adding endpoints.

## Layers

- Entry points: server actions (`src/app/**/actions.ts`) and route handlers (`src/app/api/**/route.ts`, `src/app/admin/export/route.ts`). They do transport work only: guard, parse, call a service, shape the response.
- Services and data access: `src/lib/**` (`db/store.ts`, `admin/queries.ts`, `scoring/store.ts`, `coach/*`). All SQL lives here, through Drizzle (parameterised). Entry points never build queries.
- Config and catalogues: `src/config/**`. Single source for dates, prices, disciplines.

## Every endpoint, in this order

1. Feature gate (`features.*` from `src/lib/env.ts`); disabled means 404 or a generic error.
2. Authentication and role, re-checked inside the action or handler (never rely on a layout). `requireSession` (admin only), `requireScoringSession` (judge or admin), `requireCoachSession`. A judge session must never reach personal data.
3. CSRF (`assertCsrf`) for actions; Origin check for handlers is done in `src/proxy.ts`. Machine endpoints (`/api/payments/webhook`, `/api/csp-report`) are exempt and authenticate by signature or are write-only logs.
4. Rate limit public endpoints (`rateLimit` / `rateLimitAll`, Postgres-backed). Logins use the lockout tables.
5. Validate all input with zod (`src/lib/validation/**`) or an allow-list. Ids must be UUIDs before they reach a query (store getters return null otherwise).
6. Call the service. Catch domain errors (`DuplicateApplicationError`, unique violations) and map them to a user message.

## Errors and responses

- Route handlers answer JSON `{ "error": "<short text>" }` with the right status: 400 invalid, 401/403 auth, 404 missing, 405 method, 413 too large, 429 rate limited, 503 temporary (so callers retry). Machine callbacks get 2xx for benign no-ops so providers stop retrying.
- Server actions return a typed state (`status: "error" | "saved" | ...`) with a message key or short text; never a stack or SQL error. Messages are deliberately coarse on auth paths.
- Never return or log personal data in an error.

## Config and secrets

- Read env only through `src/lib/env.ts` (zod-validated, production guard). No `process.env` elsewhere, no secrets in code. `.env.example` lists every variable.

## Logging

- Use `logger` / `securityLog` from `src/lib/log.ts`: JSON lines in production, keys are redacted by word (`email`, `name`, `age`, `token`, ...), so `message` and `page` stay visible. Event names are `domain.action` (`payment.confirmed`). Failed sign-ins are `security.login_failure`.

## Health

- `GET /api/health` liveness; `GET /api/health?deep=1` also pings Postgres (rate limited, 503 when down). Returns no detail beyond up/down.

## Database

- Schema in `src/lib/db/schema.ts`; migrations are generated by `npm run db:generate` and applied with `npm run db:migrate` over a direct (non-pooled) URL, via the manual "db-migrate" workflow, which takes a backup first. Write migrations to be re-runnable (`IF NOT EXISTS`). Never edit an applied migration.
- Pool: `src/lib/db/client.ts`, max 5 per instance in production, `prepare: false` for PgBouncer, TLS required in production.
- Index every column used in a WHERE or JOIN; unique indexes arbitrate races (duplicate guards) instead of check-then-insert.
- Known gap: several relations carry no foreign key by design (`scoring_runs.team_id`, `scoring_matches.red/blue_team_id`, `coach_sessions.coach_account_id`, `application_audit.application_id`). Adding them needs an orphan check on production data first, then a migration; do that on a Neon branch of production.
- Personal fields are encrypted in `src/lib/db/application.ts`; lookups go through blind-index hashes.

## Naming

- Files kebab-case, actions `verbNounAction` or `verbNoun`, tables snake_case plural, DB columns snake_case, TS fields camelCase.
